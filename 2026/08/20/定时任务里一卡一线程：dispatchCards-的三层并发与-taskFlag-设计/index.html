定时任务里一卡一线程：dispatchCards 的三层并发与 taskFlag 设计

发表于2026-08-20|更新于2026-08-20|后端
|浏览量:

定时任务扫出一批待处理礼品卡，如果逐张串行跑，Apple 接口一慢整轮调度就拖死；如果简单 for 循环起线程又不加控，多实例部署时同一张卡可能被派两次。

项目里 CardInitAndBoundAnonymousOrderTask 用 dispatchCards 把这个问题拆成三层：DB 抢占 → 虚拟线程派发 → Redis 执行锁。实名订单任务 RealOrderCreateTask 里也有一套同构的 dispatchOrders，思路一致。

本文只记这条派发链怎么工作、为什么需要 taskFlag 回滚、以及代码里藏了哪些设计模式。

1. 问题：定时任务下的三类并发风险

风险 场景 后果
重复派发 两个调度实例同时扫到同一张卡 重复调 Apple 接口、重复下单
并发执行 同一张卡被两个线程同时跑业务 状态机乱序、数据不一致
状态漂移 派发时状态 A，执行时已是状态 B 用过期快照做错误操作

dispatchCards 对这三类风险分别用 taskFlag CAS、Redis tryLock、加锁后重查 + statusChecker 来挡。

2. 整体架构：调度层与执行层分离

flowchart TB
    subgraph 调度层["调度层 dispatchCards"]
        A[查询 taskFlag=0 的待处理卡] --> B[CAS: taskFlag 0→1]
        B -->|失败| C[跳过，别人已抢占]
        B -->|成功| D[启动虚拟线程]
        D -->|启动失败| E[回滚 taskFlag 1→0]
    end

    subgraph 执行层["执行层 executeCardStage"]
        D -->|成功| F[Redis tryLock]
        F -->|未获得| G[直接返回]
        F -->|获得| H[重查 DB + statusChecker]
        H -->|通过| I[handler 执行业务]
        H -->|不通过| J[跳过]
        I --> K[finally: 解锁 + taskFlag 1→0]
        J --> K
        G --> K
    end

四个业务阶段都走同一套框架，只换参数：

阶段方法 threadPrefix 业务 handler

cardOrderFailCompensate cardOrderFailCompensate doCardOrderFailCompensate

3. 第一层：taskFlag CAS 抢占

调度循环里，每张卡先做条件更新：

底层 SQL 语义是：

  • task_flag = 0：空闲，可被调度
  • task_flag = 1：已派发，其他实例/线程不应再抢

这是乐观锁式 CAS，不依赖 Redis，跨 JVM 实例也能防重复派发。抢占失败直接 continue，成本极低。

为什么线程启动失败要立刻回滚？

虚拟线程若因资源/关停等原因根本没跑起来，executeCardStage 的 finally 不会执行。若不在调度层回滚，task_flag 会永久停在 1，这张卡从此再也进不了调度队列。

4. 第二层：虚拟线程一卡一线程

MdcVirtualThread 封装了 Executors.newVirtualThreadPerTaskExecutor()，并在提交时：

  1. 拷贝当前 MDC（traceId 等日志上下文）
  2. 设置线程名 cardInit-12345，方便排查
  3. 实现 SmartLifecycle，停机时 awaitTermination(300s) 等待在途任务

礼品卡处理大量时间在等 Apple HTTP、代理、Redis，属于典型 I/O 密集型。Java 21 虚拟线程让「一卡一线程」的模型几乎无额外线程栈成本，调度器线程不会被阻塞。

5. 第三层：Redis 非阻塞锁 + 二次校验

taskFlag 和 Redis 锁分工

机制 防什么 粒度 阻塞？
taskFlag CAS 重复派发 DB，跨实例 否，失败即跳过
Redis tryLock 重复执行 跨进程 否，拿不到即返回
statusChecker 过期状态执行 业务语义 —

为什么两层都要？

  • 只有 taskFlag：派发后若某实例 crash，flag 可能长时间为 1；或者极端竞态下仍可能有执行重叠窗口。
  • 只有 Redis 锁：每次调度都要抢锁，扫库 + 抢锁开销大；且无法快速过滤「已被别的实例派发但未开始执行」的卡。

组合后：CAS 在扫库阶段就过滤掉大部分冲突；Redis 锁保证真正执行业务时互斥；重查 + statusChecker 挡住「派发 → 加锁」之间的状态变化。

6. 一次完整时序

sequenceDiagram
    participant S as 调度器
    participant DB as MySQL
    participant VT as 虚拟线程
    participant R as Redis
    participant H as handler

    S->>DB: 查询 taskFlag=0 的卡列表
    loop 每张卡
        S->>DB: CAS taskFlag 0→1
        alt CAS 失败
            S->>S: continue
        else CAS 成功
            S->>VT: startVirtualThread
            alt 启动失败
                S->>DB: 回滚 taskFlag 1→0
            else 启动成功
                VT->>R: tryLock(cardId)
                alt 未获得锁
                    VT->>DB: taskFlag 1→0
                else 获得锁
                    VT->>DB: getById 重查
                    alt statusChecker 通过
                        VT->>H: handler.accept(card)
                    end
                    VT->>R: unlock
                    VT->>DB: taskFlag 1→0
                end
            end
        end
    end

7. 设计模式总结

这段代码没有显式写 interface XxxStrategy，但模式很清晰：

7.1 模板方法（Template Method）

dispatchCards + executeCardStage 固定了算法骨架：

  1. CAS 抢占
  2. 起线程
  3. 加锁 → 重查 → 执行业务 → 解锁 → 恢复 flag

具体「本阶段状态是否合法」「业务做什么」交给子步骤（传入的 statusChecker / handler）。四个 cardXxx() 方法只负责查库和填参数，不改骨架。

7.2 策略模式（Strategy）

Java 8 函数式接口把策略注入进来，避免为每个阶段写子类。例如 lockCardOrder 传入：

7.3 命令模式（Command）

handler 和虚拟线程里的 Runnable 把「做什么」封装成可延迟执行的对象，调度器只负责「何时、在哪条线程、用什么锁执行」。

7.4 乐观锁 / CAS

updateTaskFlag(id, expected, target) 是典型的 Compare-And-Swap 数据库实现：读-改-写合并为一条带条件的 UPDATE，无悲观锁表风险。

7.5 双重检查（Double-Check 变体）

第一次检查：查库时 taskFlag=0 + 业务状态条件。
第二次检查：Redis 加锁后 getById + statusChecker.test(current)。

经典 DCL 用于懒加载单例；这里是加锁后再次验证业务前提，防止时间窗口内状态变化。

7.6 装饰器（Decorator）

MdcVirtualThread.startVirtualThread 在原始 Runnable 外包一层：设置线程名、注入/清理 MDC。业务代码无感，日志 trace 不断链。

7.7 生命周期模式（SmartLifecycle）

虚拟线程执行器实现 Spring SmartLifecycle，getPhase = MAX_VALUE - 1，保证停机时先停调度器、再等业务虚拟线程跑完，避免 half-done 的礼品卡任务被硬杀。

8. 与实名订单任务的同构复用

RealOrderCreateTask.dispatchOrders 结构几乎相同，只是实体换成 RealNameOrder、锁 key 换成 REAL_ORDER_LOCK、状态校验用 expectedStatus 整数比较。

说明这套「CAS 派发 + 虚拟线程 + Redis 执行锁」是可复用的并发任务框架，不绑死在礼品卡领域。

9. 使用与排查建议

启动/扩容：多实例同时跑定时任务没问题，CAS 会自动分流；观察日志里 已被其他线程执行 是正常现象，不是 bug。

卡住不动：查 task_flag=1 且长时间不变的卡——可能是进程被 kill 在执行层中间态；需要运维回滚 flag 或等锁超时（tryLock 未阻塞，一般会快速释放）。

日志定位：线程名 {threadPrefix}-{cardId}，配合 MDC traceId 可以串起一次派发的全链路。

10. 小结

dispatchCards 不是简单的 for + new Thread，而是用三层机制各管一段：

  1. taskFlag CAS — 廉价地防重复派发，跨实例有效
  2. 虚拟线程 — I/O 密集场景下一卡一线程，调度线程不阻塞
  3. Redis tryLock + 重查 — 执行期互斥，挡住状态漂移

再叠加模板方法 + 策略注入，四个礼品卡阶段共用一套骨架，实名订单任务也复用同一模式——这是定时任务场景里比较干净的一种并发分层写法。
