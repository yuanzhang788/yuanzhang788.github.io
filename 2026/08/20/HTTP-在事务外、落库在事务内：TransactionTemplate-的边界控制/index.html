HTTP 在事务外、落库在事务内：TransactionTemplate 的边界控制

发表于2026-08-20|更新于2026-08-20|后端
|浏览量:

电商下单、支付回调、定时对账——很多流程都是「先调外部接口，再根据结果写库」。写法上常见一行：

前面可能已经做完参数校验、库存预检、调支付网关；到这里第三方已经返回了，才进入「保存结果」。

问题不是「怎么写事务」，而是事务边界画在哪：HTTP 调用和 DB 落库能不能包在同一个 @Transactional 里？常见结论是——不能。本文记这条边界怎么划，以及 TransactionTemplate 怎么用。

1. 典型流程：先调外部接口，再写多张表

以「创建订单并调用支付网关」为例：

sequenceDiagram
    participant App as 应用
    participant Pay as 支付网关
    participant DB as 数据库

    App->>App: 校验参数、查库存
    App->>Pay: 发起支付（HTTP）
    Pay-->>App: PaymentResponse
    Note over App,DB: 以下进入 TransactionTemplate 事务
    App->>DB: INSERT orders
    App->>DB: INSERT payment_records
    App->>DB: UPDATE inventory

persistOrderResult 在一次事务里通常要做多件事：

操作 表 含义
orderService.save 订单表 记录订单号、金额、状态
paymentRecordService.save 支付流水 审计：请求/响应、成功/失败
inventoryService.deduct 库存表 扣减库存、更新状态

成功：订单 → 已支付，库存扣减。
失败：写失败订单和流水，库存不变或释放预占。

这几步必须原子——订单写成功但库存没扣，或流水写了订单没写，都会造成对账灾难。

2. 为什么不用 @Transactional？

直觉是在 persistOrderResult 上加 @Transactional(rollbackFor = Exception.class)。这个方法本身可以加，但整段 createOrderAndPay 不能加。

如果把 HTTP 调用也包进事务：

会带来这些问题：

问题 原因
连接池耗尽 事务持有 DB 连接，HTTP 等待期间连接不释放
长事务锁 行锁/间隙锁持有时间过长，阻塞其他写操作
回滚无意义 支付网关已扣款成功，DB 回滚救不了外部副作用
代理失效 定时任务类里 private 方法、this. 自调用，@Transactional 可能根本不生效

推荐做法：

  • 事务外：所有 I/O（HTTP、MQ、Redis、文件读写）
  • 事务内：仅多表 DB 写入

TransactionTemplate 让你用代码精确画出这条线，不依赖 AOP 代理。

6. @Transactional 与 TransactionTemplate 怎么选

场景 推荐
Service 层标准 CRUD，方法即事务边界 @Transactional
定时任务 / 非代理类，或需缩小事务范围 TransactionTemplate
事务中嵌套不同传播行为 TransactionTemplate 或 REQUIRES_NEW
HTTP / MQ / 文件 I/O 与 DB 写混合 I/O 在外，仅 DB 段用 TransactionTemplate
需要返回值 execute
纯写库无返回 executeWithoutResult

一句话：事务跟着「最小 DB 写单元」走，不跟着「整个业务方法」走。

7. 常见坑

7.1 异常被吞掉不回滚

要么重新抛出，要么 status.setRollbackOnly()。

7.2 在 lambda 里调异步方法

异步线程拿不到当前事务的连接，要么全同步写，要么用消息 / Outbox 模式。

7.3 不必要的只读事务

如果回调里只有 getById 没有写，开事务仍有开销。有多处写时再包事务才划算。

7.4 外部调用成功后的补偿

支付已扣款但落库失败时，DB 回滚救不了。需要：

  • 幂等键防重复扣款
  • 失败重试 / 对账任务补单
  • 必要时调网关退款接口

这是分布式一致性问题，不是单靠事务能解决的。

8. 适用场景一览

场景 事务外 事务内
下单 + 支付 调支付网关 写订单、流水、扣库存
退款 调退款 API 更新订单状态、写退款记录
定时同步 拉取第三方数据 批量 upsert 本地表
消息消费 解析消息体 更新业务状态 + 写消费日志

共性：I/O 耗时长、不可回滚；DB 写入短、需要原子性 → 用 TransactionTemplate 卡边界。

9. 小结

  • HTTP 在事务外 — 不占连接、不拉长锁
  • 多表写在事务内 — 原子性、可回滚
  • TransactionTemplate — 编程式控制边界，不依赖 AOP 代理

看到 transactionTemplate.executeWithoutResult，可以把它理解成：「前面的 I/O 都做完了，从这里开始，DB 要么全写成功，要么当没发生过。」
