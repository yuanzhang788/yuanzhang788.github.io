从零搭建云上代理池：基于阿里云抢占式 ECS 的动态代理服务架构解析

这不是一篇讲 WireGuard / OpenVPN 隧道的文章，而是对真实生产项目的拆解——一个用 Spring Boot 写的、以阿里云抢占式实例为底层资源的 HTTP 代理池服务（项目代号 vpn）。它解决的问题很实在：如何用最低的成本，随时拿到一批干净、可用、可独占的海外代理 IP。

1. 项目背景：这个”VPN 模块”到底是什么

先纠正一个直觉：目录名是 vpn，但它不是传统意义的 VPN。传统 VPN 解决的是”加密隧道打通网络”，而本项目做的是动态 HTTP 代理池：

在阿里云海外区域（日本 / 新加坡 / 美国）批量拉起抢占式实例（Spot Instance，价格通常只有按量付费的 1~2 折），实例上预置 HTTP 代理服务，通过一套 REST API 对外提供代理节点的 获取 / 创建 / 释放 / 独占 管理。

为什么用抢占式实例？因为代理节点的业务特征是短生命周期、可随时替换——被释放了再拉起一台就是。抢占式实例 90%+ 的价格折扣，让它成为代理池的天然底座。

项目的几个硬性约束（决定了下文的所有设计）：

约束 影响
抢占式实例随时可能被回收 必须自动预热补足、异步回收、状态自愈
代理 IP 是稀缺资源，不能乱发 独占机制 + useType 去重 + 实例上限
多账号、多区域、价格波动 配置驱动 + 定时刷新价格候选 + 选最便宜的创建
每个 ECS 实例都花钱 用不完就释放，删除队列异步批量回收

2. 整体架构总览

两条流量路径（项目演进的结果）：

  1. 新版路径（推荐，API 直连实例）：GET /api/proxy/server/get 直接返回 ip:port，实例注册表在 Redis 中实时维护，业务方拿 ip:port 自己配 HTTP 代理使用。
  2. 旧版路径（内部队列）：FastProxyGuardExecTask.getProxy() 从 Redis 的 vpn:proxy:queue 队列 rightPop 节点，带过期校验 + TCP 连通性检测 + 复用倍数（multiple）释放阈值。README 已标注为旧版取用路径。

4. 核心设计一：多账号多区域配置模型

4.1 配置结构

application.yml 中 aliyun.proxies 是一个配置组列表，每组代表一个阿里云账号，组内可挂多个 ECS 区域：

4.2 关键概念

概念 格式/说明
proxyCode 配置组标识（多账号区分），未配置时自动生成 proxy-0、proxy-1
serviceKey {proxyCode}:{ecsIndex}:{endpoint}，如 jp-sgp-main:1:ap-southeast-1，唯一标识一个”账号×区域”服务单元
regionCode 对外业务区域：JP / SGP / US（RegionCode 枚举）
active-proxy-count 预热目标数（0 = 不预热，但 API 仍可按需创建）
max-proxy-count 创建硬上限（预热与 API 都受此约束）

4.3 启动装配

AliServerProxyService.init() 在 @PostConstruct 时遍历配置，为每个”账号×区域”构建一个 EcsService 实例（持有独立的 ECS/VPC Client、配额、标签），并以 serviceKey 为 key 存入 ImmutableMap：

配额校验有个防御逻辑：active > max 或负数时，直接 fallback 到 1/3 并打 error 日志——配置错了宁可保守也不放开。

这个模型的价值：多账号天然隔离（每个配置组有自己的 AK/SK），多区域聚合对外统一暴露 regionCode，调用方完全感知不到内部账号路由。

5. 核心设计二：价格感知的候选调度

这是本项目最”值钱”的部分：创建实例时不是随机选，而是实时选最便宜的。

5.1 候选生成链路

关键点：查价是 I/O 密集型，全部用 CompletableFuture + 20~40 线程池并行，候选多时收益巨大。

5.2 三层 Redis 缓存（避免打爆阿里云 OpenAPI）

缓存 Key 内容 TTL
vpn:proxy:specs:{serviceKey} 该区域可用规格集合 分钟级
vpn:proxy:resources:{serviceKey} 该区域可用资源（可用区×规格） 分钟级
vpn:proxy:price:{regionId}:{zoneId}:{specs}:{cloudType}:{diskSize} 单价（BigDecimal 字符串） 小时级
vpn:proxy:disk:{spotStrategy}:{regionId}:{specs} 规格支持的磁盘类型 小时级
vpn:proxy:vswitch:{serviceKey}:{zoneId} 交换机 ID（含 Pending 轮询等待） 小时级

缓存未命中 → 实时查阿里云 → 回填 Redis，降级链路清晰。

5.3 权重随机算法（旧版内部队列用）

ServiceListVO.setPrice() 里有个值得注意的设计：

价格越低权重越大，用于旧版队列的随机加权取用。虽然新版 API 路径已经直接按”最低价优先”创建，但这个权重字段保留了下来，可见项目的演进痕迹。

5.4 创建前的配额过滤

异常信息非常友好：区域 JP 已达最大代理数上限，无法创建新实例：JP(3/3)、SGP(2/3)——直接把每个区域的 当前/上限 打出来，排障不用猜。

6. 核心设计三：Redis 实例注册表

ECS 实例列表是全系统的事实来源，但每次都实时调 describeInstances 太慢。项目用 Redis 做了一层实例注册表：

6.1 Key 设计

Key 类型 说明
vpn:proxy:instance:{proxyCode}:{regionId}:{instanceId} String(JSON) 实例详情 DTO
vpn:proxy:instance:index:{serviceKey} Set 该 service 下的实例 ID 索引
vpn:proxy:exclusive:{proxyCode}:{regionId}:{instanceId} String 独占标记（setIfAbsent 实现）
vpn:proxy:used-types:{proxyCode}:{regionId}:{instanceId} Set 已使用的 useType 集合

6.2 读取路径（批量 + 去脏）

mget 批量读取 + 自动清理脏索引，这个细节很务实——实例被抢占回收后，Redis 里的脏数据必须能自愈。

6.3 状态自愈三件套

时机 行为
启动时 hydrateProxyInstanceRegistry() ApplicationReadyEvent 后，全量调 describeInstances 把存量实例灌入注册表
每 5 秒 syncPendingProxyInstances() 对非 Running 状态的实例逐个刷新（ProxyInstanceStatusSyncTask）
创建后 waitForCreatedProxyServer() 轮询最多 createPollMaxAttempts 次（默认 3 次、间隔 1s），直到实例 runing 且有公网 IP

isAllocatable() 的定义是核心判定：

只有 Running 且拿到公网 IP 的实例才允许对外分配——状态机：created(Pending) → wait_start(Starting) → runing(Running) → devastate(其他)。

7. 核心设计四：分配策略（独占与去重）

7.1 三种分配模式

7.2 独占 = Redis 分布式锁

  • setIfAbsent（SETNX）天然原子，多实例部署也安全；
  • TTL 可配置（兜底防死锁），但默认语义是主动归还：POST /api/proxy/server/exclusive/return；
  • 归还接口做了容错：实例已不存在时仅清理标记，不额外操作 ECS。

7.3 useType 去重（业务隔离）

useType 的设计很妙：同一个业务类型（如 order）拿到的代理不会重复，但不同业务类型可以共享同一台机器。实现上每个实例维护一个 used-types Set，SADD 成功（返回 1）才算抢到：

批量判断时用 pipeline 一次查所有实例的独占/已用状态（fillExclusiveFlags / batchUsedByType），避免 N 次 RTT。

7.4 失败回滚

finalizeProxyServerAllocation() 处理了组合失败的情况：独占成功但 useType 标记失败 → 回滚独占标记，保证不残留半状态。

8. 核心设计五：异步删除队列

释放 ECS 是异步的：release 只是把任务丢进 Redis List，后台每 1 秒消费。这是为了避免突发释放时把阿里云 OpenAPI 打爆。

细节：

  • deleteBatchInstance 用阿里云 DeleteInstances 批量接口（1~100 台/次），而不是逐台删；
  • 分组键是 proxyCode:regionId，因为不同账号的实例必须用对应 AK 的 client 删；
  • 删除成功后要清理三处 Redis 残留：独占标记、useType 标记、实例注册表；

9. 核心设计六：预热与水位控制

9.1 目标水位

每个 serviceKey 有两个水位：active（期望池容量） 和 max（硬上限）。预热的目标是把”池中就绪数”补到 active。

9.2 触发链路

9.3 预热防并发

每个 serviceKey 一把 ReentrantLock（warmupLocks），tryLock 失败直接跳过——避免多个定时任务/请求同时触发创建：

每轮还有 warmupMaxPerTick 上限，防止一次预热太多台。预热线程池用 newCachedThreadPool（daemon 线程），不阻塞主流程。

9.4 “就绪”口径

池容量 = Running + 有 IP + 未独占 + 无 useType 标记，口径严格，避免”数着有 5 台，实际能发出去的只有 1 台”的错觉。

10. 动态 IP 模块（IPIPGO 接入）

除了自建 ECS 代理池，项目还接了一个第三方动态 IP 服务 IPIPGO，作为补充通道：

参数 说明 约束
num 提取数量 1~500
cc 国家代码（逗号分隔多国） 可选
state / city 地区 / 城市 可选
life IP 时效（分钟） 3~60
protocol 1=http/https，2=socks5 可选

实现的亮点：

  1. 参数默认值合并：请求参数与配置默认值合并（mergeQuery），调用方可以只传关心的参数；
  2. 出站代理支持：访问 IPIPGO 时可选先走自己的代理（outboundProxy.enabled，支持账号密码认证）——用自己代理池的 IP 去提取第三方 IP，避免本机 IP 被 IPIPGO 风控；
  3. 日志脱敏：maskKeyInUrl() 把 URL 里的 key=***，防止 AppKey 泄漏进日志；
  4. 响应容错：非 200 状态码抛异常，业务失败 code 透传，success/code 双判断。

11. 操作审计

关键操作异步写入 MySQL 表 proxy_server_operation_record（MyBatis-Plus）：

操作 operation_type 触发接口
获取代理 GET GET /api/proxy/server/get
释放实例 RELEASE POST /api/proxy/server/release
归还独占 EXCLUSIVE_RETURN POST /api/proxy/server/exclusive/return

审计字段：requestRegionCode、exclusiveRequested、proxyCode、regionId、serverId/ip/port、callerIp、callerPlatform（从 X-Platform 等请求头推断，兜底 UA）、status（SUCCESS/FAIL）、message（截断 512 字符）。

两个工程细节：

  1. 审计失败不影响主流程——recordOperation 内部 try-catch，只打 error 日志。数据库挂了代理照常发。
  2. 调用方平台识别：支持 X-Platform / Platform / X-Client-Platform / X-App-Platform 四个请求头，未传时从 User-Agent 推断。这是典型的 To-B API 审计设计。

12. API 一览

方法 路径 说明
GET /api/proxy/server/get 获取代理（推荐）：有现成直接返回，没有自动创建并轮询
POST /api/proxy/server/create 仅创建（可指定 count，需同时传 regionCode）
GET /api/proxy/server/list 实例列表（regionCode 过滤 + 多账号聚合）
GET /api/proxy/server/stats 状态统计（总数 + 各区域 Running/Pending/Starting/Other）
POST /api/proxy/server/release 释放单台（入删除队列，异步）
POST /api/proxy/server/release-all 释放全部（返回 totalCount/successCount/failCount）
POST /api/proxy/server/exclusive/return 归还独占
GET /api/proxy/ip/get IPIPGO 动态 IP 提取

统一响应 Result<T>：code（200 成功）/ msg / data / timestamp。

安全设计：proxyCode（内部账号标识）在返回前被 sanitize* 方法置空——对外只暴露 regionCode，不暴露账号路由细节。

13. 踩坑与工程经验

13.1 时区坑（UTC vs UTC+8）

阿里云 API 返回的时间是 UTC，且自动释放时间的格式还可能有秒、可能没有秒。项目用 DateTimeFormatterBuilder 做了容错解析，再统一 +8 输出：

创建实例时 createEcsServer 里还有一条注释特别醒目：

抢占式实例的 autoReleaseTime 只支持最长 1 小时（spotDuration=1 / 手动设），所以创建后必须再用 modifyInstanceAutoReleaseTime 校准更长的保留期——instanceAutoReleaseTime() 里同样有 +8 校正注释。

13.2 两种 RedisTemplate 的共存

  • StringRedisTemplate：价格、规格等字符串缓存；
  • RedisTemplate<String, Object>（RedisConfig.OBJ qualifier）：对象序列化，用于实例注册表、删除队列（存 DeleteInstanceDTO 对象）、multiGet 批量读。

删除队列消费时对历史脏数据做了双格式兼容（对象 / Map / JSON 字符串三种解析），说明线上换过序列化方案，兼容代码是血泪教训留下的。

13.3 并发控制全家桶

场景 手段
多区域并行查价 20~40 线程 ThreadPoolExecutor + CompletableFuture
创建限流 Semaphore(5)
预热防重 每 serviceKey 一把 ReentrantLock + tryLock
删除防重 batchLock 全局锁 + 单线程调度器
独占原子性 Redis setIfAbsent（SETNX）

13.4 主动健康检查（旧版队列）

ProxyChecker 用 1s 超时的 TCP connect 探测代理端口连通性；FastProxyGuardExecTask.getProxy() 拉取节点时若探测失败，会触发 closeProxyServer 回收——发出去的节点必须能用，这是代理服务的底线。

14. 可改进方向

基于代码现状，列出几个我看到的优化空间（也算给自己的 TODO）：

  1. Redis 独占标记防死锁：目前 TTL 是兜底，可以引入 Lease（续租）机制，或归还时校验持有者（对比 value 里的 sid）。
  2. 实例注册表与真实 ECS 的对账：目前依赖定时刷新 + 消费时清理，可以考虑周期性全量 describeInstances 做差量对账，自动清理幽灵索引。
  3. 价格缓存的时效性：价格按小时缓存，抢占式价格波动快，可对热点规格缩短 TTL。
  4. 创建失败的类型化降级：createEcsServer 失败目前直接抛异常，可区分”库存不足 / 配额超限 / 网络错误”做不同重试策略。
  5. 审计表分区/归档：GET 操作量大，长期运行建议按月分表或归档。
  6. IPIPGO 结果落库：动态 IP 提取后可以本地缓存去重，减少第三方调用成本。

15. 总结

把这个项目过完一遍，最值得学习的是它的成本意识和状态管理：

维度 设计
省钱 抢占式实例 + 价格感知调度 + 用不完即释放 + 批量删除
可靠 实例注册表 + 启动 hydrate + 定时状态同步 + 删除队列重试归队
并发安全 SETNX 独占 + 双重锁 + 信号量 + pipeline 批量检查
业务隔离 useType 去重分配 + 多账号聚合 + proxyCode 对外隐藏
可观测 Knife4j 文档 + 全链路操作审计 + 结构化日志

一句话：这不是一个”VPN 模块”，而是一个把云计算资源当成”可编程代理池”来运营的完整系统——它把”云上资源的创建、分配、回收、审计”全部服务化，对外只暴露一个干净的 HTTP 接口。这种”资源即服务”的思路，值得每一个做基础设施开发的工程师借鉴。
